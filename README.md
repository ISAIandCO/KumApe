# KumApe

В версии **0.3.11** общее ядро подключено из отдельного репозитория [ApeShareCore](https://github.com/ISAIandCO/ApeShareCore) как библиотека с закреплённым SHA. [Модули, контракты и автоматические PR обновления](docs/shared-core.md).

<p align="center"><img src="assets/branding/KumApe.png" width="300" alt="KumApe"></p>

Экспериментальное Firefox-расширение для аналитика Kaspersky KUMA. Идея та же, что у [ApePatrol](https://github.com/ISAIandCO/ApePatrol): меньше ручного копирования между карточкой события, поиском и TI-порталами. Реализация при этом отдельная и рассчитана на модель данных и API KUMA.

> [!IMPORTANT]
> Версия `0.3.6` — технический preview для KUMA 4.6. Используемые REST-маршруты сверены с официальной схемой KUMA Public API 3.0; чтение карточки через DOM и локальные mappings процессов всё ещё нужно проверить на реальной инсталляции.

## Что уже есть

- чтение полей открытой карточки KUMA через `kuma-id` / `kuma-data`;
- чтение Raw из области «Исходное событие»;
- копирование события и ссылки на него;
- связанные события по IP, узлу, учетной записи, процессу, command line, файлу, хешу, домену и URL;
- открытие нативного Threat Hunting KUMA через URI с закодированными SQL и периодом, без зависимости от DOM редактора;
- «Полезные фильтры»: выпадающий каталог с подсказкой по отсутствующим полям, SQL-preview и редактируемыми шаблонами для узлов, учётных записей, процессов, сети/DNS, HTTP, файлов, хешей и правил;
- интерактивный граф процессов parent→child с отрисовкой и раскладкой ApePatrol, свободным/временным/пошаговым режимами, закрепляемыми карточками, regex-фильтрами и настройкой сил;
- локальные расследования с timeline, заметками, тегами и экспортом JSON/Markdown;
- локальный AI-чат через OpenAI-compatible endpoint с preview и режимами Strict/Redacted/Full;
- редактируемые профили полей для Windows Security, Sysmon, PowerShell и Linux auditd;
- поиск через `POST /api/v3/events` с выбором storage cluster;
- отдельная проверка REST API и Bearer-токена;
- постраничное получение всех доступных storage clusters;
- просмотр расширенной схемы полей KUMA;
- меню 🐵 рядом с IOC в карточке KUMA: проверки через API VirusTotal, Kaspersky OpenTIP и AbuseIPDB, результаты в меню и ссылки на отчёты;
- read-only получение ресурса correlation rule по его ID;
- проверка текущей web-сессии через `GET /api/whoami`;
- разрешение Firefox только на конкретные адреса KUMA, указанные пользователем.

Расширение не запрашивает логин или пароль KUMA и не выполняет изменяющих API-запросов. Токен KUMA и ключи IOC-провайдеров хранятся в `storage.local` и сохраняются после перезапуска Firefox и обновления расширения. Они не синхронизируются через Firefox Sync. Сохранившийся токен из `storage.session` переносится автоматически; уже утраченный старой версией ключ нужно ввести заново.

## Установка для проверки

Нужен Node.js 20+ и системная утилита `zip` только для упаковки.

```bash
npm test
npm run build
```

После сборки:

1. Откройте в Firefox `about:debugging#/runtime/this-firefox`.
2. Нажмите **Load Temporary Add-on / Загрузить временное дополнение**.
3. Выберите `dist/firefox/manifest.json`.
4. Откройте KUMA и нажмите иконку KumApe.
5. Разрешите доступ к адресу веб-интерфейса и REST API.

Архив для установки собирается командой:

```bash
npm run package
```

Результат появится в `artifacts/`.

## Сборка и релиз на GitHub

Workflow **CI** запускается для каждого pull request и push в `main`. Он выполняет тесты, собирает ZIP для ревью, проверяет воспроизводимость каталога расширения и сохраняет архив `kumape-firefox-review` в артефактах запуска.

Workflow **Release signed XPI** запускается вручную из GitHub Actions на нужном commit. Для него в настройках репозитория должны быть заданы secrets `AMO_JWT_ISSUER` и `AMO_JWT_SECRET` от Mozilla Add-ons API. Workflow:

1. собирает self-hosted вариант с `update_url`;
2. получает у Mozilla unlisted-подпись;
3. проверяет ID, версию и адрес обновлений внутри XPI;
4. создает `updates.json`, SBOM, архив исходников и SHA-256 checksums;
5. публикует GitHub Release с тегом `v<version>`.

Перед повторным запуском релиза нужно поднять версию в `package.json` и `package-lock.json`: существующий GitHub tag не перезаписывается.

## Настройка KUMA

Расширению нужны два входа в KUMA Core:

```text
Web UI:   https://kuma.example.local:7220
Core API: https://kuma.example.local:7223
```

В распределённой установке адреса коллекторов и storage-узлов указывать не нужно: запросы API идут в Core, а нужное хранилище выбирается как `clusterID`. Если Core работает в HA, укажите адрес балансировщика/VIP. При нескольких доступных кластерах KumApe потребует выбрать конкретный, а не возьмёт первый молча.

Для поиска нужны **GET `/api/v3/events/clusters` и POST `/api/v3/events`**. POST выполняет SQL-поиск, а не запись: одних GET-прав недостаточно, и сервер вернёт 403. Также нужен доступ пользователя к выбранному кластеру и тенанту; для остальных функций — права чтения соответствующих ресурсов. Экспорт расширенной схемы доступен администраторам и Tier 2 Analyst; при меньших правах ожидаем ответ `403`, остальные функции продолжат работать. Если используется внутренний сертификат, сначала откройте оба адреса в Firefox и подтвердите доверие сертификату.

В настройках находится JSON-редактор профилей related search. Рекомендуемый стартовый набор включён по умолчанию; его можно изменить под локальные normalizer/extra normalization/extended schema или полностью отключить, оставив общие нормализованные поля.

Каталог «Полезных фильтров» также редактируется в настройках. Каждый фильтр содержит `id`, `name`, `description`, SQL-условие `template`, диапазон `timeRange` и флаг `enabled`. Подстановки вида `${SourceAddress}` берутся из открытого события и экранируются перед построением SQL; нормализованные числовые поля (например, порты и PID) подставляются как проверенные числовые литералы без кавычек. Логические подстановки `${@host}`, `${@account}`, `${@process}`, `${@ip}`, `${@file}`, `${@hash}`, `${@domain}`, `${@url}` и `${@command}` используют фактические поля активного профиля. В popup применимые фильтры находятся сверху, а для остальных прямо в списке указаны отсутствующие поля.

Поля графа процессов не входят в JSON related search. Они задаются отдельными карточками по схеме «поле Event ID + значение Event ID + допустимые `DeviceEventCategory` → поля события»: host, PID, Parent PID, GUID, image, command line, user и ID события KUMA. Категория обязательна для встроенных Windows 4688 и Sysmon 1, чтобы одинаковые короткие Event ID других источников не попадали в граф. Старые настройки `processGraph` автоматически переносятся в эту форму. Встроенные mappings являются стартовыми и должны быть сверены с нормализаторами конкретной KUMA.

## Локальный AI

KumApe обращается только к явно включённому OpenAI-compatible endpoint на этом компьютере или в локальной сети (например, `http://192.168.1.10:8080/v1`). Поддерживаются private IPv4, локальные IPv6 и локальные имена; публичные адреса и облачный fallback заблокированы. Для endpoint можно сохранить отдельный необязательный API-ключ: он хранится в `storage.local` и передаётся только в заголовке `Authorization: Bearer`.

Перед первым запросом отдельная вкладка показывает режим приватности, список полей и размер контекста. В режиме Strict не передаются `Raw`, `Extra`, cookies и произвольные расширенные поля; Redacted маскирует поля и фрагменты с признаками секретов; Full отправляет полное событие только после явного выбора этого режима и нажатия пользователем кнопки.

Подробности и статус endpoint-ов: [docs/kuma-api-notes.md](docs/kuma-api-notes.md). Карта REST, web API, DOM и полей событий: [docs/kuma-surfaces-and-fields.md](docs/kuma-surfaces-and-fields.md). Сценарий проверки на реальной KUMA: [docs/manual-tests.md](docs/manual-tests.md).

## Почему не копия ApePatrol

У MaxPatrol SIEM и KUMA разные API, поля событий и устройство веб-интерфейса. Поэтому KumApe использует простой поток:

```text
карточка KUMA → content extractor → popup → background → KumaAdapter → read-only API
```

DOM используется для получения открытого события. Поиск выполняется через публичный REST API, где это возможно. Read-only web API рассматривается как отдельная поверхность: он изолирован в адаптере и не считается стабильным, пока его не подтвердит Network/Fetch/XHR в KUMA 4.6.

## Что пока не включено

- автоматическое дозапрашивание дополнительных временных окон графа;
- объединение расследований между аналитиками;
- редактирование Active Lists, правил и ресурсов;
- AI tools, облачный fallback и автоматические действия модели;
- автоматическая отправка IOC внешним сервисам;
- перехват сетевых запросов или учетных данных KUMA.

Эти функции имеет смысл добавлять после проверки базового spike на реальной системе и фиксации фактических ответов API.

## IOC в карточке

В настройках KumApe сохраните отдельные ключи нужных TI-провайдеров и разрешите Firefox доступ. Кнопка «Сохранить и проверить» сразу проверяет сохранённый ключ запросом отчёта для `8.8.8.8`; окончание реально сохранённого ключа отображается в поле. Затем рядом с IP, доменом, URL или хешем в карточке KUMA нажмите 🐵 и выберите «Проверить». AbuseIPDB доступен для IP, VirusTotal и OpenTIP — для всех перечисленных типов. Ответ или ошибка появятся в том же меню; оно следует за полем при прокрутке и закрывается по Escape, клику снаружи или повторному нажатию кнопки.

Внешние запросы не выполняются при открытии карточки или меню. Передаётся только выбранное значение IOC; событие и Raw целиком не отправляются. Запрашиваются существующие отчёты: файлы не загружаются, новые сканирования не запускаются. Кнопки «Открыть отчёт» работают без API-ключа. Ключ каждого провайдера можно удалить отдельно; пустое поле при сохранении не стирает существующий ключ.
