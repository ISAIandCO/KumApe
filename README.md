# KumApe

<p align="center">
  <img src="assets/branding/KumApe.png" width="300" alt="KumApe">
</p>

<p align="center">
  <b>Firefox-компаньон для расследований в Kaspersky KUMA</b>
</p>

**KumApe** — расширение для Firefox, которое добавляет в **Kaspersky KUMA** инструменты, полезные при повседневном расследовании: связанные события, граф процессов, готовые SQL-фильтры, IOC-проверки, локальные расследования и AI-ассистента.

Идея та же, что у [ApePatrol](https://github.com/ISAIandCO/ApePatrol): меньше ручного копирования между карточкой события, поиском, расследованием и TI-сервисами. Но реализация отдельная — под модель данных, API и особенности интерфейса KUMA.

Начиная с **0.3.11**, часть общего функционала ApePatrol и KumApe вынесена в отдельную библиотеку [ApeShareCore](https://github.com/ISAIandCO/ApeShareCore). Общими остаются только автономные компоненты; работа с KUMA по-прежнему живёт в самом KumApe.

> [!IMPORTANT]
> Основная цель сейчас — **KUMA 4.6**. REST API сверялся с официальной схемой KUMA Public API 3.0, но DOM карточки события, локальные маппинги и некоторые особенности конкретных инсталляций KUMA всё ещё требуют проверки на реальной системе.

> [!NOTE]
> KumApe — независимый open-source проект. Он не связан с AO Kaspersky Lab, не одобрен компанией и не является официальным компонентом Kaspersky KUMA.

## Что уже умеет KumApe

### Работа с событиями

KumApe читает открытую карточку события и добавляет несколько вещей, которых обычно не хватает при ручном расследовании.

Можно:

* получить поля события и Raw;
* скопировать или скачать JSON;
* скопировать ссылку на событие;
* добавить событие в расследование;
* найти связанные события;
* открыть результаты поиска в штатном Threat Hunting KUMA;
* проверить IOC прямо из карточки;
* получить правило корреляции по его ID.

Для связанных событий можно искать по:

* IP;
* узлу;
* учётной записи;
* процессу;
* command line;
* файлу;
* хешу;
* домену;
* URL.

Поиск идёт через `POST /api/v3/events`, а нужный storage cluster выбирается явно.

---

### Полезные фильтры

В KumApe есть каталог готовых SQL-фильтров для типовых задач расследования.

Например:

* процессы;
* хосты;
* учётные записи;
* IP и порты;
* сетевые соединения;
* DNS;
* HTTP;
* файлы;
* хеши;
* правила и Event ID.

Фильтры показываются выпадающим списком: те, которые можно применить к текущему событию, идут первыми. Для остальных сразу видно, каких полей не хватает.

Перед запуском SQL можно посмотреть и при необходимости отредактировать.

<details>
<summary><b>Как устроены шаблоны фильтров</b></summary>

<br>

Каталог редактируется в настройках.

У каждого фильтра есть:

* `id`;
* название;
* описание;
* SQL-шаблон;
* диапазон времени;
* флаг включения.

Можно использовать прямые подстановки полей:

```text
${SourceAddress}
```

или логические значения:

```text
${@host}
${@account}
${@process}
${@ip}
${@file}
${@hash}
${@domain}
${@url}
${@command}
```

Логические значения разрешаются через активный профиль полей.

Строки экранируются перед формированием SQL. Числовые поля вроде PID и портов проверяются и подставляются как числа без кавычек.

</details>

---

### Граф процессов

Для процессных событий можно построить интерактивный граф **parent → child**.

Визуальная часть и базовая механика графа общие с ApePatrol.

Есть три режима:

* **Связи** — обычный граф процессов;
* **По времени** — представление с временной привязкой;
* **Пошаговый** — начинаем с одного события и расширяем только интересующую цепочку.

В пошаговом режиме из карточки процесса можно отдельно найти родителя или дочерние процессы, не пересобирая весь граф.

<details>
<summary><b>Что ещё есть в графе</b></summary>

<br>

* закрепляемые карточки узлов;
* regex-фильтры;
* фильтрация событий;
* настройка сил графа;
* дедупликация событий по KUMA `ID`;
* исключение корреляционных событий `Type = 3`;
* сохранение уже найденной цепочки при дополнительном поиске;
* переход из узла к соответствующему событию в KUMA;
* возможность увеличить выборку с 1000 до 10 000 событий.

По умолчанию для Windows 4688 используется пара:

```text
DeviceCustomString5 → PID
DeviceCustomString3 → Parent PID
```

Если она не заполнена:

```text
DestinationProcessID → PID
SourceProcessID      → Parent PID
```

Hex PID при необходимости приводятся к decimal.

Для Sysmon 1 и Windows 4688 дополнительно проверяется `DeviceEventCategory`, чтобы события других источников с тем же коротким Event ID случайно не попадали в граф.

</details>

<details>
<summary><b>Настройка полей процессов</b></summary>

<br>

Маппинги графа задаются отдельно от профилей связанного поиска.

Для каждого типа события можно указать:

* поле Event ID;
* значение Event ID;
* допустимые `DeviceEventCategory`;
* host;
* PID;
* Parent PID;
* GUID;
* image;
* command line;
* user;
* ID события KUMA.

Встроенные варианты — это стартовая конфигурация. На реальной KUMA их желательно сверить с используемыми нормализаторами, extra normalization и extended schema.

</details>

### Расследования

События можно собирать в локальные расследования, не покидая расширение.

В расследовании есть:

* timeline;
* заметки;
* теги;
* поиск;
* сортировка;
* удаление объектов;
* переход обратно к событию KUMA;
* динамический граф сущностей;
* сравнение событий;
* выбор событий и заметок для AI.

Готовое расследование можно экспортировать в **JSON** или **Markdown**.

### IOC-проверки

Рядом с IP, доменом, URL или хешем в карточке KUMA появляется меню 🐵.

Через API можно проверить значение в:

* **VirusTotal**;
* **Kaspersky OpenTIP**;
* **AbuseIPDB**.

Также можно просто открыть готовый отчёт в браузере — для этого API-ключ не нужен.

<details>
<summary><b>Как работают IOC-проверки</b></summary>

<br>

Ключи провайдеров задаются отдельно в настройках.

Кнопка **«Сохранить и проверить»** сразу делает тестовый запрос и показывает окончание реально сохранённого ключа. Если сервис отвечает `401`, KumApe прямо сообщает, что сохранённый ключ был отклонён провайдером.

Внешний запрос выполняется только после нажатия пользователем.

Передаётся **только выбранный IOC**:

* событие целиком не отправляется;
* Raw не отправляется;
* файлы не загружаются;
* новые сканирования не запускаются.

Запрашиваются только уже существующие отчёты.

Меню привязано к полю события и остаётся рядом с ним при прокрутке карточки.

</details>

---

### Локальный AI

В KumApe есть встроенный чат с **OpenAI-compatible API**.

Он рассчитан в первую очередь на локальные модели: сервер может работать на этом же компьютере или в локальной сети.

Например:

```text
http://192.168.1.10:8080/v1
```

Публичные AI-endpoint'ы и облачный fallback специально заблокированы.

История и черновик сохраняются, а в один диалог можно добавлять события из текущей вкладки KUMA или расследования.

<details>
<summary><b>Что отправляется модели</b></summary>

<br>

Перед запросом можно посмотреть точный JSON, который получит модель.

Есть три режима.

**Strict**

Не отправляются:

* `Raw`;
* `Extra`;
* cookies;
* произвольные расширенные поля.

**Redacted**

Дополнительно маскируются поля и фрагменты, похожие на секреты.

**Full**

Можно отправить полное событие, но только после явного выбора режима пользователем.

Для каждого события, добавленного в чат, применяется выбранный режим приватности.

</details>

<details>
<summary><b>Подключение локального AI</b></summary>

<br>

Разрешены:

* private IPv4;
* локальные IPv6;
* локальные имена узлов.

Для endpoint можно сохранить отдельный необязательный API-ключ.

Он хранится в `storage.local` и передаётся только как:

```text
Authorization: Bearer ...
```

AI tools, автоматические действия модели и облачный fallback пока не включены.

</details>

---

### Профили полей

Нормализация KUMA может заметно отличаться между инсталляциями, поэтому используемые KumApe поля можно переопределять.

Есть редактируемые стартовые профили для:

* Windows Security;
* Sysmon;
* PowerShell;
* Linux auditd.

Профили можно адаптировать под собственные normalizer, extra normalization и extended schema.

Если специфические поля не нужны, можно оставить только общие нормализованные поля KUMA.

## Настройка KUMA

KumApe нужны два адреса KUMA Core:

```text
Web UI:    https://kuma.example.local:7220
Core API:  https://kuma.example.local:7223
```

В распределённой установке адреса storage-узлов и коллекторов указывать не нужно.

Все запросы идут через Core, а конкретное хранилище передаётся как `clusterID`.

Если Core работает в HA, лучше указать адрес балансировщика или VIP.

При наличии нескольких storage clusters KumApe попросит выбрать нужный и не станет молча использовать первый попавшийся.

<details>
<summary><b>Какие права нужны</b></summary>

<br>

Для поиска событий нужны:

```text
GET  /api/v3/events/clusters
POST /api/v3/events
```

Важно: `POST /api/v3/events` здесь выполняет **поиск**, а не изменение данных.

Поэтому API-ключ только с GET-правами для поиска не подойдёт — KUMA вернёт `403 Access denied`.

Также пользователю нужен доступ:

* к выбранному storage cluster;
* к нужному tenant;
* на чтение тех ресурсов, с которыми работает расширение.

Экспорт расширенной схемы доступен администраторам и Tier 2 Analyst. Если прав недостаточно и KUMA отвечает `403`, остальные функции KumApe продолжат работать.

Если используется внутренний сертификат, сначала откройте Web UI и Core API вручную в Firefox и подтвердите доверие сертификату.

</details>

## Безопасность

KumApe не запрашивает логин или пароль KUMA и не выполняет изменяющих API-запросов.

Токен KUMA и ключи TI-провайдеров хранятся локально в Firefox и не синхронизируются через Firefox Sync.

Сохранённые настройки переживают перезапуск браузера и обновление расширения.

<details>
<summary><b>Подробнее</b></summary>

<br>

Секреты хранятся в:

```text
storage.local
```

Старый токен, найденный в `storage.session`, переносится автоматически. Если ключ уже был потерян предыдущей версией расширения, восстановить его невозможно — его нужно ввести заново.

KumApe не делает автоматически:

* IOC-запросы при открытии события;
* отправку события внешним сервисам;
* загрузку файлов;
* изменение правил;
* изменение Active Lists;
* перехват учётных данных;
* перехват сетевых запросов страницы.

Firefox получает разрешение только на те адреса KUMA и внешних API, которые нужны пользователю.

</details>

## Почему это не просто ApePatrol для KUMA

MaxPatrol SIEM и KUMA довольно сильно отличаются: у них разные API, модель событий, поля и устройство веб-интерфейса.

Поэтому общий поток KumApe выглядит примерно так:

```text
карточка KUMA
      ↓
content extractor
      ↓
popup
      ↓
background
      ↓
KumaAdapter
      ↓
read-only API KUMA
```

DOM используется в основном для получения уже открытого события.

Поиск, где это возможно, выполняется через публичный REST API.

Неофициальный read-only web API изолирован в отдельном адаптере и не считается стабильной частью интеграции, пока его поведение не подтверждено на реальной KUMA.

Общие с ApePatrol автономные части постепенно выносятся в **ApeShareCore**, чтобы исправления и улучшения не приходилось реализовывать дважды.

## Что пока не делаем

Некоторые вещи специально оставлены за рамками текущего этапа:

* автоматическое расширение временного диапазона графа;
* совместные расследования нескольких аналитиков;
* изменение Active Lists, правил и других ресурсов KUMA;
* AI tools;
* автоматические действия модели;
* облачный AI fallback;
* автоматическая отправка IOC внешним сервисам;
* перехват сетевых запросов или учётных данных KUMA.

Сначала имеет смысл стабильно проверить чтение событий, поиск и маппинги на реальных инсталляциях KUMA.

<details>
<summary><b>Текущие ограничения</b></summary>

<br>

Одна выборка событий по умолчанию ограничена **1000 событиями**.

Если лимит достигнут, его можно явно увеличить до **10 000**.

Это всё равно не гарантирует полную историю процесса: остаются ограничения заданного периода поиска и фактической доступности событий в KUMA.

DOM/API конкретной инсталляции и визуальный результат графа также желательно проверять вручную.

</details>

<details>
<summary><b>Установка из исходников</b></summary>

<br>

Нужен **Node.js 20+**.

Системная утилита `zip` нужна только для упаковки.

Проверка и сборка:

```bash
npm test
npm run build
```

После этого:

1. откройте в Firefox `about:debugging#/runtime/this-firefox`;
2. выберите **«Загрузить временное дополнение»**;
3. укажите `dist/firefox/manifest.json`;
4. откройте KUMA;
5. нажмите иконку KumApe;
6. разрешите доступ к Web UI и Core API.

Для получения установочного архива:

```bash
npm run package
```

Результат появится в каталоге:

```text
artifacts/
```

</details>

<details>
<summary><b>CI и выпуск XPI</b></summary>

<br>

Workflow **CI** запускается для pull request и push в `main`.

Он:

* выполняет тесты;
* собирает ZIP для ревью;
* проверяет воспроизводимость каталога расширения;
* сохраняет `kumape-firefox-review` в артефактах запуска.

Для выпуска подписанного XPI используется workflow **Release signed XPI**.

В GitHub Secrets должны быть:

```text
AMO_JWT_ISSUER
AMO_JWT_SECRET
```

Workflow:

1. собирает self-hosted версию с `update_url`;
2. получает unlisted-подпись Mozilla;
3. проверяет ID, версию и update URL внутри XPI;
4. создаёт `updates.json`;
5. создаёт SBOM;
6. упаковывает исходники;
7. считает SHA-256;
8. публикует GitHub Release с тегом `v<version>`.

Для повторного выпуска нужно сначала увеличить версию в:

```text
package.json
package-lock.json
```

Существующий GitHub tag автоматически не перезаписывается.

</details>
